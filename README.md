# AWS IAM Access Control Lab: Enforcing Least Privilege and Multi-Factor Authentication

## Overview
The goal of this project was to build a small but realistic identity governance model — the kind of foundational access control that any organization running workloads in the cloud needs, regardless of size. Rather than granting broad or default permissions, every identity created in this lab is scoped down to the minimum access required to do its job, and every login is required to prove it's not just a password, but a verified user.

**Skills demonstrated:**
- IAM user, group, and policy management
- Least privilege access design using AWS managed policies
- Custom IAM policy authoring (JSON) with condition-based access control
- Multi-factor authentication (MFA) enforcement
- Governance thinking: mapping technical controls back to security principles

## Step 1: Securing the Root Account

Before creating any IAM resources, I enabled MFA on the AWS account's root user. Root credentials have unrestricted access to the account, so this is the first and most important control in any AWS environment — a compromised root account bypasses every other IAM control put in place afterward.

A virtual MFA device was registered to the root user using an authenticator app, clearing AWS's built-in security recommendation for the account.

![Root MFA enabled](images/root-mfa-enabled.png)

## Step 2: Creating a Least-Privilege User Group

Rather than attaching permissions directly to individual users, I created a group called `SecurityAnalysts` to represent a job function. Managing permissions at the group level — rather than per-user — is a core least-privilege practice: it keeps access consistent, auditable, and easy to scale as more users are added or removed.

The group was attached to the AWS-managed **`ReadOnlyAccess`** policy, which grants visibility across AWS services without allowing any create, modify, or delete actions. This models a real analyst role: someone who needs to observe and investigate, but not make changes.

![SecurityAnalysts group created with ReadOnlyAccess attached](images/group-created-readonly.png)

---

## Step 3: Creating an IAM User

A user, `sanalyst01`, was created to represent a fictional security analyst and added directly to the `SecurityAnalysts` group during creation (rather than attaching policies to the user individually). This ties the user's entire permission set back to the group, so their access changes automatically if the group's policies ever change.

Console access was enabled with an autogenerated password and a forced password reset on first login — a standard control that prevents a shared or admin-set password from persisting long-term.

![User added to SecurityAnalysts group with ReadOnlyAccess inherited](images/user-added-to-group.png)

---

## Step 4: Enforcing MFA on the User

With the user created, I assigned a virtual MFA device to `sanalyst01`, the same control applied to the root account in Step 1. This ensures that even read-only access requires proof of identity beyond a password — closing off one of the most common attack vectors (credential theft/phishing) for any account with console access.

![MFA device assigned to sanalyst01](images/user-mfa-assigned.png)

## Step 5: Building a Custom Conditional Access Policy

AWS doesn't have a feature literally called "Conditional Access" the way Entra ID does, but it has an equivalent mechanism: **IAM policy conditions**. I wrote a custom policy, `RequireMFAPolicy`, that denies nearly all AWS actions unless the requester's session shows `aws:MultiFactorAuthPresent = true` — with a narrow exception carved out for the handful of actions a user needs to set up MFA in the first place.

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyAllExceptListedIfNoMFA",
            "Effect": "Deny",
            "NotAction": [
                "iam:CreateVirtualMFADevice",
                "iam:EnableMFADevice",
                "iam:GetUser",
                "iam:ListMFADevices",
                "iam:ListVirtualMFADevices",
                "iam:ResyncMFADevice",
                "sts:GetSessionToken"
            ],
            "Resource": "*",
            "Condition": {
                "BoolIfExists": {
                    "aws:MultiFactorAuthPresent": "false"
                }
            }
        }
    ]
}
```

This is a well-established AWS pattern for enforcing MFA at the policy level, rather than relying on users to opt in voluntarily. Reviewing the policy summary before creation confirmed the intended effect: an explicit deny applied across all 475 AWS services shown in the console, each carrying the `aws:MultiFactorAuthPresent` condition.

![Custom MFA-enforcement policy JSON](images/mfa-policy-json.png)
![Policy summary showing explicit deny across all services](images/mfa-policy-summary.png)

---

## Step 6: Attaching the Policy to the Group

The final step was attaching `RequireMFAPolicy` to the `SecurityAnalysts` group, alongside the existing `ReadOnlyAccess` policy. This means every current and future member of the group inherits both controls automatically: scoped-down read-only visibility, and a hard requirement to authenticate with MFA before that access can be used for anything beyond initial MFA setup.

![SecurityAnalysts group with both policies attached](images/group-final-policies.png)

## Governance Notes

The controls in this lab map directly to core principles found in frameworks like NIST 800-53 (AC-2, AC-6, IA-2) and ISO/IEC 27001 Annex A — specifically around access control, least privilege, and multi-factor authentication for privileged and non-privileged accounts alike. The intent here wasn't to claim formal compliance with either framework, but to show that the underlying reasoning — grant only what's needed, verify identity strongly, and manage access through repeatable group-based assignment rather than one-off exceptions — was applied deliberately rather than left to default settings.

---

## Conclusion

This lab set out to build a small, realistic identity governance model in AWS: a group-scoped least-privilege role, a user provisioned into that role rather than granted ad hoc permissions, and a policy-enforced MFA requirement layered on top. Along the way, it also involved adapting when the original platform choice (Entra ID) hit an unresolvable technical blocker — a reminder that real security work often means working around tooling problems, not just following a clean tutorial path.

Next steps for this project would include extending the policy to require MFA conditionally based on IP range or time of day (a closer analogue to full Conditional Access), and adding a small automation script using the AWS CLI or SDK to handle bulk user provisioning or periodic access reviews.
